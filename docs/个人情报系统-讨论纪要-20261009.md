## 变更记录 · 2026-10-31（当前有效方向，优先级高于全文其他章节）

### 为什么改方向

现状是一个完整的 AI 工具集：知识库、AI 打分、AI 打标签、复习卡、间隔调度全部打通。但**所有 AI 调用都是用户点按钮触发的固定流程**——流程由人排，AI 只负责填空。
参赛作品的判据只有一条：**有没有「AI 自己决定下一步做什么」的环节**。据此做结构性改造：加一个对话入口 + 一个循环 + 一个确认环节，把既有能力包成 agent 可调用的工具。

### 赛事与期限（已确认）

- **作品提交截止：2026-11-10**（用户与组委会确认，组委会已改期）。《作品提交说明》里的"10-20 24:00"与官网旧报名窗口均作废，不再按那两处排期。
- 从 2026-11-01 起**只剩 10 天，且零缓冲日**；任务清单里"超期即砍"的降级规则必须真的执行。
- 报名费 80 元/人；组别：本科生组 / 通用赛道 / 教育领域。
- 交付物：PPT **20 页（官方模板结构，按格子填，不是自由发挥的方案文档）**、视频 **6 分钟**、可访问的线上环境 + 评审账号密码。

### 三条硬性门槛（《作品提交说明》原文换算）

1. 「智能体链接以及相关文档/账号与密码」→ **必须有账号体系**，评委要能自己登录。本地 8081 打不开的网页不算作品。此前"鉴权以后再上、交给舍友"的安排作废，**登录升为必做项**。
2. 「提交作品内不得出现学校、学生姓名和指导教师信息」→ 盲审：PPT、视频、界面截图均不得出现校名 / 本人姓名，**演示账号也不能用真名**。
3. 「至少 3 个契合主题的提示词示例，并展示输出结果」→ 注意这是**至少 3 条演示提示词 + 输出结果**，不是"至少 3 个工具"。必须提前定死 3 条并截图，不能临场发挥。

### 部署与录制的时序约束

部署 + 账号密码必须**提前 5 天**完成（压到最后一天就来不及出 3 条示例截图与录屏）；视频最后录，但同样要留提前量。

PPT 官方 20 页结构（节选）：作品背景 1 页 / 数据来源 1–2 页 / 知识库内容 1–2 页（公共教育语料与用户私有学习档案**两者隔离**）/ 预处理与利用 1–2 页（**要流程图**；MdParser、JsonlParser、TagNormalizer、ImportService 是现成素材）/ 分析方法 1–2 页 / 问题理解与逻辑论证 2–3 页（要图表 + 思维导图）/ 创新点 1 页。
**已知弱项**：数据来源这一节最薄，需要补"公共教育语料 + 私有学习档案"的说明。

### 结构性改动（四处）

1. **数据层**：`knowledge` 加 `summary`（一句话摘要，agent 检索只读它）、`status`（`DRAFT` / `ACTIVE`，支撑"确认才入库"）、`user_id`（账号归属）。**原计划的 `raw_content` 已砍**，正文继续用 `content`（理由见 2026-11-01 记录）。
2. **摄入**：加 `poi-ooxml`，新增 `PptxParser` / `DocxParser`，与既有 `MdParser` / `JsonlParser` 统一为 `String parse(File)` 按扩展名分发。只支持 `.pptx` / `.docx`，不碰 `.ppt` / `.doc`；pptx 抽出的文字零散，主演示用 md/docx。
3. **归纳**：`AiService.generateSummary()` **一次调用**返回四件套 `{title, summary, tags, points}`（分开调会各说各话且更贵）。摘要**在入库时算好存下**，对话时只读 `summary` 列——不是每次对话现算。
4. **Agent 循环**：`AgentService`，先给 4 个工具 —— `searchKnowledge`（只回标题 + 摘要）、`readKnowledge`（**按 id 读全文**，id 是句柄不是标题）、`listDueCards`、`createReviewCards`；循环**最多 8 轮**防烧钱。前端对话页必须把"正在查询知识库…找到 3 条…"这类步骤露出来，评委看的是过程。

### 一个必须先解决的坑：加列不能写进启动脚本

`spring.sql.init.mode=always` 每次启动都跑 `schema.sql`，而 SQLite **没有 `ADD COLUMN IF NOT EXISTS`**——`ALTER TABLE` 第二次启动就会 `duplicate column name` 致服务起不来。
**采用方案**：把新增各列直接写进 `schema.sql` 的 `CREATE TABLE` 语句，**删除本地 `knowledge.db` 重建**（开发期只有测试数据）。不引入 `PRAGMA table_info` 检查组件，也不上 Flyway（两者都是一次迁移换一套机制，属过度设计）。

### 复习卡改多张（T4 副产品）

`ReviewService.createCards` 由"一知一卡"改为遍历 `points` 生成 N 张；幂等判据仍按 `knowledge_id`（生成过就直接返回）。
**有意放弃**：不给 `review_card` 加 `point_index`（卡与知识点的对应关系），因为幂等策略让"逐点增删"场景不会出现；真需要时再加列，成本十分钟。
**已知影响**：一条知识 3 个点 → 3 张卡同时 `stage=1`、`next_review_at=now`，首页待复习数量一次跳 3，属预期行为。

### 明确不做（本赛期一条都不碰）

情报管道 / collector / 爬虫（**功能一整节冻结**，与"教育"主题无关，做了就交不上）、向量库 / RAG / Embedding（200 条笔记用关键词足够）、Redis / Docker / 微服务（Redis 的评估理由与拒绝话术见 2026-11-01 记录）、MCP 封装（评审只登录网页，没有其他 agent 调用场景，但可作为"评估过所以没做"的讲述素材）、多智能体、books / co-writer / 可视化 / 视频课、遗忘曲线（缺 `review_log` 历史数据，改用百分比）。

### 任务清单与顺序（10 天版）

- T0（非代码，卡着一切）：核实截止时间（**已完成：作品提交 11-10，组委会改期**）、**报名 + 缴费 + 组队**（待用户办理）、确认是否要求线上环境。报名未办则后续全部悬空。
- D1–D2：T1 改表（删库重建）+ T2 解析器。目标：**当天能看到"上传 md → 入库"**，正反馈最快。
- D3：T3 `generateSummary` + T4 上传→归纳→确认→入库（`DRAFT` → `ACTIVE` → 打标签 → 按 points 建 N 张卡）。
- D4（新增，因硬门槛 1）：**账号体系最小版** —— `user` 表 + 登录页 + JWT + **预置演示账号**（不做注册/找回密码）；`knowledge` 加 `user_id` 列并在 Mapper 按用户过滤。列现在就加，将来扩多用户零迁移。代价约 1.5 天，从 T5 的时间预算里扣。
- D5–D7：T5 `AgentService` 循环。**最小版只给 `searchKnowledge` + `createReviewCards` 两个工具**即可（硬门槛要求的是 3 条演示提示词，不是 3 个工具）；`readKnowledge` / `listDueCards` 第二迭代加。
- D8：T7 对话页 + T8 复习百分比。
- D9：T9 部署 + 评审账号（**提前完成**）+ 定死 3 条演示提示词并截图。
- D10：T10 PPT（官方 20 页结构）+ T11 视频（6 分钟）。
- 降级顺序（任何一项超期就砍）：**T6 会话记忆 → T8 百分比 → T4 的确认环节**（退化为生成即入库）。
- T6 会话记忆（每次对话结束提炼"在学什么/卡在哪/下次从哪继续"并注入下次）排在 **D8 收尾的最后一个任务，做不完即砍**，是观感加分项而非评判项。

## 变更记录 · 2026-11-01（T1 数据层设计定稿 · 本轮四问结论）

### T1 走方案乙：DRAFT 落库，不做"前端暂存预览"

- **采用**：解析 + AI 归纳后**立刻 INSERT**，`status = DRAFT`；确认接口只做 `UPDATE ... SET status='ACTIVE'`。
- **代价（已知并接受）**：不点确认的草稿会积攒成"幽灵数据"。它是脏数据但不影响任何功能（agent 查询一律带 `WHERE status='ACTIVE'`），最多首页多个"丢弃"按钮。判断依据：**脏数据在数据库里是廉价的，状态在浏览器里丢失是昂贵的。**
- **否决的候选**：①"前端暂存预览、确认后一次性提交"——刷新即丢、AI 调用白花钱、还得在浏览器里手搓一个草稿库、做不出"待确认 N 条"；②为草稿单独建 `knowledge_draft` 表——两套 Mapper/Service 或一个转换层，典型过度设计。

### 砍掉 `raw_content`

`content` 装的就是解析出来的正文，而确认页只让改标题 / 摘要 / 标签、**不改正文**，所以 `raw_content` 与 `content` 完全同源，等于同一份文本存两遍、每次写入都要同步两个字段（漏一处就是静默 bug）。**正文只留 `content`**，`raw_content` 从表结构和代码中一并抹掉。

### 结论：T1 只加 `summary` / `status` / `user_id` 三列

- `summary`：入库时由 `generateSummary` 写好，检索层只读它。它**不是"给人看的读后感"，而是给模型判断"要不要展开"的判别特征**——这个定位决定了摘要的写法。
- `status`：`DRAFT` 草稿 / `ACTIVE` 正式；它是**人做的闸门，不是分类**，且对 agent 完全不可见（`DRAFT` 被 `WHERE status='ACTIVE'` 隔离）。
- `user_id`：**T1 就加，D4 才建 `user` 表与登录**。理由是避免第二次删库重建；SQLite 加列不要求被引用表已存在，外键约束留到 D4 再补。
- 加列方式仍按 10-31 记录：写进 `CREATE TABLE` + 删本地 `knowledge.db` 重建，不上 Flyway、不写 `PRAGMA table_info` 检查脚本。

### 动线（一次上传 → 一条可被 agent 检索的知识）

```
上传 → Parser 解析正文 → AiService.generateSummary（一次调用出 {title, summary, tags, points}）
     → INSERT，status=DRAFT（用户可见、agent 不可见）
     → 确认页 → 用户点确认 → status=ACTIVE → TagService 打标 → ReviewService 按 points 建 N 张卡
     → agent：searchKnowledge 读 title+summary → readKnowledge 按 id 读 content
```

### Agent 循环结构（T5 实现口径，已出流程图）

- **上下文在循环外组装一次**：系统提示词 + 用户输出规则 + 最近一次会话记忆；循环内只**追加**工具结果，不重拼（否则模型会看到重复的自己）。
- 模型每轮只有三种返回：**调工具** / **直接回答** / **反问**。后两种在技术上同一条路径——这一轮不调工具、直接吐文字，循环自然结束；所以"反问"**不需要特殊代码分支**，只需提示词约束。
- 工具结果回灌后再调一轮，**最多 8 轮**。循环的驱动权在模型身上（工具只执行被要求的动作），这条回灌箭头就是"AI 自己决定下一步"的可见载体。
- 会话记忆的提炼放在**出口**（对话结束），不在循环内——循环里模型还在忙着查东西，没空总结自己。

### 本轮四问的结论

1. **自定义输出规则** —— 用 `user` 表一个字段 `agent_rule`（**不建独立规则表**），前端给 **4 个按钮**：讲解型 / 考试型 / 苏格拉底式 / **自定义**（清空输入框自由书写）。点按钮只是把模板文本填进输入框，用户可改，保存后生效。
   **硬边界**：用户规则只拼进"最终回答"的系统提示词，**不得拼进工具调用那一步**，否则用户写"请用表格回答"会把工具调用的输出格式带沟里。
2. **会话记忆（T6）** —— 一张表 + 一次调用，排在 D8 收尾的最后一个任务、超时即砍。最小字段 `{id, user_id, note, created_at}`。价值在观感：评委第一句"我上次学到哪"，agent 直接答上来。
3. **流式输出** —— **先做假流式**：后端一次性返回，前端按约 30ms/字逐字吐。真 SSE 的难点不在推字，而在"工具步骤事件 + 文本片段"混在同一条通道的事件协议设计，需半天到一天，**有余量再上**。
4. **对话界面形态** —— 消息流 + 工具步骤条 + 输入框，**不做左侧历史会话列表**（要多一张 `session` 表和切换逻辑，属过度设计；单用户演示一个连续会话足够）。

### 采纳港大项目的 4 条（逐条对应）

- **先摘要再读全文** → T5 的 `searchKnowledge`（只回 title+summary）→ `readKnowledge(id)`（id 是句柄不是标题）。**补充约束：单次对话最多展开 3 条全文**，模型想读第 4 条要先给结论、再问用户。
- **聊完自己记一笔** → T6 会话记忆（见上）。
- **不确定先反问** → **新增，进 T4 验收标准**：上传后先问"按考试重点整理，还是按概念理解整理"；意图模糊时也必须先问而非猜。实现 = 提示词约束 + 前端把这句话渲染成可选卡片。
- **先预览别一次全给** → 确认页（DRAFT 预览）+ 上面那条"最多展开 3 条"。

### Redis：不做（可作为 PPT "评估过所以没做"的素材）

- Redis 的两个强项是**多实例共享状态**与**过期自动清理**。本项目是单用户、单实例、单进程、SQLite 本地文件，两条都用不上；读 SQLite 是毫秒级，加一层 Redis 反而更慢（多一次序列化 + IO）。
- 会话记忆的"过期"用 SQLite 加一列 `expire_at` + 查询条件即可，零部署。
- 代价：Windows 上跑 Redis 要 WSL / Docker / memurai，线上机器还得再装一遍，多一个进程就多一个崩点。按 10 天零缓冲，至少吃掉半天，收益为零。
- 真要做多实例扩展时再加，不提前付钱。

### 第②步定稿：字段语义与三个实现决定

**`summary`（TEXT，可空）**
- 由 T3 的 `generateSummary` 在上传入库那一次写入，之后不再重算。
- 允许为空（AI 超时/限流/返回不合规 JSON 时不能把整条丢掉），但空摘要会使该条检索价值为零。
- **兜底写在 Service 层**（取正文前 200 字），不写进 SQL 的 `COALESCE(..., substr(...))`——`substr` 是 SQLite 方言，业务规则不该焊死在某个数据库上。

**`status`（TEXT，NOT NULL，`DEFAULT 'ACTIVE'`）**
- 取值 `DRAFT` / `ACTIVE`；它是**人做的闸门，不是分类**，且对 agent 完全不可见。
- **默认值选 `ACTIVE`**，原则是"**默认值要选错误可见的那一个**"：默认 `DRAFT` 会让 5 个存量插入点产生的数据全部静默隐身（首页空白、agent 搜不到、且不报错）；默认 `ACTIVE` 让老路径行为零变化，新路径忘写 `setStatus("DRAFT")` 时错误是**看得见**的（草稿直接进了正式列表）。
- 不加 `CHECK` 约束（枚举只有两个值，靠 Java 常量避免拼写错误即可），不加索引（200 条数据全表扫描是微秒级，索引是负资产）。
- **它保护的不是那一条记录，是它的下游产物**：AI 写错标题时，若无闸门，错误会扩散到标签、复习卡、agent 检索结果三处，且要从最下游往回清理。
- **真实成本不在 DDL，在"每一处读都要加过滤"**：① 首页列表只查 `ACTIVE`、确认页另查 `DRAFT`（`findAll` 不能一个方法通吃）；② 详情 `findById` 只允许 `ACTIVE`；③ agent 的 `readKnowledge` 必须校验 `status='ACTIVE'`（这是安全边界，否则模型能读到未确认内容）；④ 打标签 / 建复习卡只能对 `ACTIVE` 触发。**漏任一处 = 草稿泄露，且不报错。**
- 否决 `boolean confirmed`：TEXT 一眼可读、便于调试，且留了 `ARCHIVED` 之类第三种状态的扩展位；几个字节的成本远低于改表结构的成本。

**`user_id`（INTEGER，可空）**
- D4 之后从登录态取，**在 Controller 层塞进实体**，不在 Mapper 里读 session（避免 Mapper 绑死 Web 层）。
- **D4 当天再删一次库**：Mapper 改成 `WHERE user_id = ?` 后，T1~T3 造的测试数据（`user_id = NULL`）会查不到。不写 `OR user_id IS NULL` 的兼容条件——不为开发期数据留永久垃圾。

**`agent_session_note`（新表，最小版）**
- 字段 `{id, user_id, note, created_at}`；`note` 控制在 200 字内（在学什么 / 卡在哪 / 下次从哪继续）。
- 唯一查询是"取该用户最新一条"，故**不加索引、不加 `expire_at`**。
- **自我纠正**：上一轮为论证"SQLite 也能做到 Redis 的过期"，举了 `expire_at` 的例子；按最小版设计根本不需要它——读取方式是"取最新一条"，永远读不到旧记录。不为假想需求提前建列。

**时间字段：统一由 Java 侧 `LocalDateTime.now()` 写入，格式 `2026-11-01T12:34:56`**
- 该格式**字典序 = 时间序**，`ORDER BY` 与范围比较可直接用。
- **禁止在 `schema.sql` 用 `DEFAULT (datetime('now'))`**：它产出 `2026-11-01 04:34:56`（空格分隔 + **UTC**），与本地时间混列会字符串乱序，且只在跨月时暴露。
- 澄清：`LocalDateTime.now()` 取 JVM 本地时区，中国机器就是北京时间，**不是"中国不能用"**；坑只在"UTC 与本地时间混用"。
- **采用方案 C：抽 `Timestamped` 接口**，`Knowledge` / `User` / `AgentSessionNote` 都 `implements`，`TimestampAspect` 由 `instanceof Knowledge` 改为 `instanceof Timestamped`。
  - 否决方案 B（在切面里继续加 `instanceof` 分支）：切面会退化成类型路由器，每加一张表都要回来改。
  - 否决方案 A（各 Service 手写）：与"Knowledge 走注解"不一致，后来人（含舍友）会困惑。
  - 门槛依据：只有 1 个实现时不抽接口，**现在有 3 个实现且诉求相同，抽接口才有价值**。

**`user` 表：交给舍友建，不进本次 `schema.sql`**

## 0. 一句话定位（功能一 · 个人情报系统，2026-10-31 已冻结，请勿开工）

把最初设想的"实时爬虫"重新定义为：

> **定时采集 + 分层筛选 + 限额推送 + 反馈学习** 的个人情报系统。

采集器是**入口**（信息涌进来）→ 知识库是**沉淀**（一键收入，留下来的才是自己的）→ Vue 看板是**消费**（日常浏览）。三者构成个人知识闭环。

## 1. 三个关键判断（反省机制，先立认知）

### 1.1 "实时"是伪需求，放弃
- 源的节奏：GitHub Trending 天级、掘金热榜小时级、AI 大新闻一天几条；人的消费节奏：早晚各一次。
- 秒级抓取会逼出 7×24 常驻进程、反爬对抗、频率控制、代理，复杂度翻三倍，收益为零。
- 正确方案：**定时批量**（早 8 点早报 + 晚 8 点补一次），技术上就是一个定时任务。
- 原则：**需求的频率由消费者决定，不由生产者决定。**

### 1.2 真正的难点是"筛"，不是"抓"
- 同类项目典型死法：接七八个源 → 推送三天 → 通知一关再也不打开。死因是**通知疲劳**（notification fatigue，通知太多导致彻底麻木）。
- 一天推 30 条 = 一条没推。
- 抓取是全项目最简单的部分；决定生死的是**筛选质量**和**推送节奏**。

### 1.3 为什么现成产品（Follow / Inoreader / AI 日报频道）之外还要自己造
- 纯获取信息：自己写不划算。
- 自己造的两个不可替代价值：
  1. **反馈闭环**：根据点击/忽略越来越懂自己，数据全在本地；
  2. **学习价值**：定时任务、HTTP、数据建模、第三方 API、AI 应用、系统设计、消息推送的全栈综合练习场，且全部用正在学的技术。
- 定位：**练手 + 自用产品为主，信息获取为顺带收益。** 防止在"要不要再加几个源"上无限膨胀。

## 3. 核心设计：四层筛选漏斗

核心思想：**便宜的粗活机器干，贵的细活 AI 干，最懂你的活自己干。**

### 第 0 层 · 源头控制
- garbage in, garbage out：只订阅关心的 GitHub topic（如 java / spring-boot / llm）、掘金指定标签和认可作者。
- 信息质量上限在选源时就已决定。

### 第 1 层 · 硬规则粗筛（免费、快；几百条→三五十条）
- **看 star 增速而非总数**（最重要认知）：10 万 star 上榜无意义；两天 50→800 才是信号。需要 `star_history` 表，每次记数字算 24h 增量。**速率比存量重要。**
- 关键词白名单/黑名单：命中 spring、agent 加权；"课程/变现/资料领取"降权。
- 去重（dedup）：同一内容多平台转载只留一条。
- **多源交叉印证**（反向利用重复）：GitHub 涨星 + 掘金分析 + HN 讨论同时出现 → 重加权。
- 实现建议：分数可拆解记录，如 `热度+30 / 关键词+20 / AI+40`。

### 第 2 层 · AI 精筛（贵，只对粗筛幸存者调用；→十几条）
- 直接复用 `AiService` 模式，Prompt 升级两点：
  1. 评"对**我这个人**的相关性"而非泛泛的内容质量（注入画像：正在学 Java、Spring Boot、Web 全栈、AI 应用开发的初学者）；
  2. 强制输出四件套：**分数 / 一句话摘要 / 推荐理由 / 分类**（可直接用的工具 · 教程 · 行业动态 · 值得深读的长文）。
- 成本：粗筛后每天约 30 条，DeepSeek 一天几分钱。漏斗的经济意义就在这。

### 第 3 层 · 反馈闭环（区别于换皮 RSS 阅读器的护城河 moat）
- 每条三个操作：**收藏 / 点进去看了 / 不感兴趣**，行为写回数据库。
- 定期统计（如"近 20 条 AI 新闻忽略 17 条"）→ 自动降权该分类，或把事实加进下次 AI Prompt。
- 接受**冷启动**（cold start）：前两周系统比较笨，需耐心喂反馈，别三天判死刑。

## 4. "发到桌面让我看见"的方案

结论：**飞书机器人负责主动提醒，Vue 日报页负责安静浏览，就这两个渠道。** 不在桌面端技术上恋战。

1. **飞书机器人 webhook（推荐）**：往对方给的网址 POST 数据即发消息，手机电脑同时收到，免费，本机有飞书环境。推手机比推桌面更不易错过。
2. **早 8 点自动打开日报页**：定时任务跑完用 Java 自带 `Desktop.browse()` 打开本地 Vue 页面，开机自启后自动弹出，零成本仪式感。
3. Windows toast（右下角现代通知）：Java 原生 `SystemTray` 只支持老式气泡，现代通知要绕 PowerShell，属 hack（取巧不正规），后期再说。
4. 常驻桌面悬浮窗：JavaFX 或 Electron（引入整套 Node.js，偏离 Java 主线），明显后期。
5. 浏览器 Web Notification：需常驻标签页，别扭。

## 5. 展示层设计（怎么一眼看出重要性）

1. **分级 + 限额，而非平等列表**：
   - **S 级：每天最多 3 条**，才允许飞书主动推，附 AI 写的"为什么今天必须看"；
   - **A 级**：进日报页，不打扰；
   - **B 级**：只躺在看板里可翻，不出声。
   - "最多 3 条"是精髓：逼筛选器提高标准 + 保护注意力。
2. **分数可解释（explainability）**：卡片显示拆分项 `热度+30（24h涨600⭐）｜关键词+20｜AI+40`。烂推荐时知道调哪个旋钮，透明才会信任，信任才愿意持续反馈。
3. **AI 一句话摘要前置**：不点进去就知道值不值得读，把判断成本降到最低。
4. **周报聚类（clustering，相似内容自动归并）**：每周日 AI 通览本周入库内容，输出"本周 AI Agent 方向 6 条，共同趋势是 XXX"——从接收**信息**升级为收到**洞察**。

### 信息源扩展（按性价比排序）
- MVP：**GitHub 官方 API**（topic + 创建时间过滤）
- 之后：**Hacker News**（官方 API 免费，国外技术风向，极客密度高）
- **各大模型官方博客 RSS**（OpenAI/Anthropic/DeepSeek，一手信源比媒体快一天且无标题党）
- **掘金**（无正式开放 API，克制调网页接口）、V2EX 酷客节点
- 架构要点：写一个通用 `RssCollector` 即可接入全世界几百万博客，一本万利。

## 6. 架构设计：管道思维

系统是一条**管道（pipeline，数据像水流经每一节，每节只干一件事）**：

```
采集层            归一化层          粗筛+去重        AI 精筛          分发层
Collector    →    Normalizer   →    Filter     →    Scorer    →    Dispatcher
每源一个类         各源格式→统一      规则/热度         打分/摘要        飞书/日报/沉默
                                          ↓ 每层数据都落库
                                   SQLite：items / star_history / feedback
        一个 @Scheduled 定时任务，每天按点把整条管道从头推到尾
```

### 必须刻意练习的动作：统一接口（契约）

```java
// source：来源。所有信息源遵守同一份契约
public interface NewsSource {
    List<RawItem> fetch();   // fetch：抓取；每个源各自实现
}
```

`GithubCollector` / `JuejinCollector` / `HnCollector` / `RssCollector` 各自实现；主流程只拿 `List<NewsSource>` 循环调用。
**加新源 = 新建一个类，主流程一行不改** —— 开闭原则（对扩展开放、对修改关闭）在自己项目里的第一次真实落地。

### 包结构（在现有 com.example.kb 内长）

```
com.example.kb
├── collector/              ← 新管道的地盘
│   ├── NewsSource.java          （接口：统一契约）
│   ├── GithubCollector.java
│   ├── JuejinCollector.java
│   ├── model/                   （RawItem 原始条目、统一 Item）
│   ├── filter/                  （关键词、去重、热度规则）
│   └── dispatch/                （飞书推送、日报生成）
├── service/ ...           ← 现有业务层，AiService 直接复用
└── controller/ ...        ← 现有层不动
```

### 不新开项目的理由与纪律
- 理由：数据库、AI 服务、前端、启动脚本全复用；且"采集→一键入库→浏览"是一个闭环，拆两个项目会切断闭环。
- 纪律：采集代码全部关进 `collector` 包，不许与现有知识库代码揉团。**复用能力，但隔离边界。**

## 10. 2026-10-11 追加：功能二 · 复习系统（间隔重复）

> 状态：方案讨论完毕，未动手。**优先级建议待拍板**（见 10.5）。

### 10.1 总评与优先级建议

- 方向完全正确，可能是知识库最值得长的功能；与情报系统构成完整闭环：**爬虫发现 → 收入知识库 → 复习消化**。
- **建议提为"第 0 步"，排在爬虫之前**，三个理由：
  1. **纯本地闭环**：无外部 API、无合规问题、无反爬对抗；数据（现有 knowledge 表）现成；
  2. **当天就有价值**：爬虫要等外部源喂，复习系统今天做完明天就能对已有条目发起第一轮复习；
  3. **天作之合**：添加知识的 `@PostMapping`（KnowledgeController）就是天然挂载点（hook：在既有流程的固定位置插入新逻辑）。

### 10.2 三个修正（对原始设想的纠偏）

**修正一：固定"艾宾浩斯复习表"是科普版，行业标准是自适应调度**
- 固定时间表（20分/1时/1天/2天/4天/7天/15天/30天）源自 1885 年无意义音节实验的简化版，入门够用但不匹配时代。
- 现代标准：**间隔重复**（spaced repetition，按个人实际遗忘情况动态安排下次复习）：
  - **SM-2 算法**（1987，Anki 用了三十年）：`下次间隔 = 上次间隔 × 难度系数(ease factor)`，约 15 行代码，适合先读懂再写；
  - **FSRS**（Free Spaced Repetition Scheduler）：2023 年底起成为 Anki 默认调度器，开源界最先进；官方有多语言实现（Python/TS/Rust 等），Java 移植版存在——**实现阶段再核实具体库名与活跃度，不猜版本**。
- MVP 决策：**先用"固定阶梯 + 忘了回炉"跑通系统，算法藏在独立类里**，将来换 SM-2/FSRS 只换一个实现类。顺序是"先跑通，再变聪明"，反了会重蹈九平台项目覆辙。

**修正二：复习必须是"主动回忆"，不能是"再看一遍"**
- 认知科学结论：**重读（re-reading）是弱复习，检索练习（retrieval practice，主动从脑子里掏答案）才是强复习。**"扫一眼内容 → 哦对 → 关掉"记忆几乎不增长。
- 数据模型关键判断：**知识条目 ≠ 复习卡**。一张合格的卡 = 一个问题 + 一个答案。
- 核心设计：**添加知识时用现有 `AiService` 自动生成 1~3 张复习卡**（Prompt 从"打分"换成"提炼问答对，返回 JSON 数组"）。零手工制卡——"制卡太累"正是 Anki 用户弃坑第一死因，本系统在此天然占优。
- 复习交互闭环：看问题 → 心里作答 → 翻面对照 → 自评（记得/模糊/忘了）→ 评分喂回调度算法（也是将来升级 FSRS 的训练数据）。

**修正三："直接弹窗到桌面"之前有个硬约束——后端必须活着**
- 弹窗和飞书推送**全部由本地 Spring Boot 进程发出**，进程不跑，一切提醒都不会发生。这个基础设施问题要在设计期暴露，别等实现期撞上。
- 路线 A（**推荐**）：**开机自启后端**——给 start.bat 做自启变体，放进启动文件夹或用任务计划程序（Task Scheduler）在登录时用 `javaw`（无控制台窗口的 Java 启动器）静默拉起。保持一个系统、一条技术线。
- 路线 B（不推荐）：Windows 计划任务跑独立小脚本直读 SQLite 文件发提醒——解耦但引入第二条技术线、两套运行时。
- 防通知疲劳（老原则在此更适用）：**一天一次打包提醒（"今天有 N 张卡到期"），绝不一卡一弹**。复习被碎片化打断 ≈ 新闻被刷屏淹没。
- 实现坑：飞书交互卡片按钮需要飞书服务器回调本机接口，本机无公网地址——**MVP 推送只做提醒（附 localhost 链接），全部打分交互在本地复习页完成**。

```

│   ├── ReviewCardMapper.java      （MyBatis 映射）

│   ├── FixedLadderScheduler.java  （MVP 实现：固定阶梯）
│   ├── ReviewService.java         （业务：到期查询、评分更新、生成卡片）
│   └── ReviewController.java      （复习页 API）
├── service/AiService.java         （已有，新增 generateReviewCards 方法）
└── config/ReviewReminderTask.java （@Scheduled 每日任务：查到期→推送）

新表 review_card：
  id, knowledge_id, question, answer,
  stage（当前阶梯阶数）, next_review_at, last_reviewed_at, status
```

**review_card 独立成表**（不把调度字段塞进 knowledge 表）的两个理由：
1. **单一职责**：知识条目的职责是"存内容"，复习卡的职责是"被考试"；
2. **一对多**：一条知识可产出多张卡，塞原表表达不了。

调度算法契约（开闭原则第二次落地）：

```java
// scheduler：调度器。定义"复习完之后，下次什么时候再考我"的契约
public interface ReviewScheduler {
    LocalDateTime nextReview(int stage, RecallQuality quality);
    // stage：当前处于复习阶梯的第几阶
    // RecallQuality：自评枚举（REMEMBERED 记得 / FUZZY 模糊 / FORGOT 忘了）
}
```

每日流程：

```
@Scheduled 每天 8:00
   → 查 next_review_at <= 今天的卡
   → 飞书推送"今天 N 张卡到期" + 本地页面链接（/ SystemTray 气泡）
   → 打开复习页：看问题 → 作答 → 翻面 → 自评
   → FixedLadderScheduler 算出下次时间，写回 next_review_at
```

MVP 阶梯参数（去掉科普表的 20分/1时——"每天一批"模式下日内间隔无意义，呼应"频率由消费者决定"）：

```
1天 → 2天 → 4天 → 7天 → 15天 → 30天 → 60天
记得：进下一阶    模糊：原地重排    忘了：回炉第 1 阶
```

### 10.4 范围纪律（明确不做什么）

Anki 是本领域三十年王者，最大风险是做成 Anki 山寨版。**砍掉**：牌组/标签管理、富文本卡片（图片/音频/LaTeX）、统计图表、多用户、导入导出（将来真需要可导出 Anki 的 `.apkg` 格式白嫖其复习体验）。

**MVP 只做五件事**：AI 生成卡、到期查询、复习页交互、自评更新调度、每日一次打包提醒。

### 10.5 拍板记录（2026-10-11）

1. ✅ 优先级接受：复习系统为"第 0 步"，爬虫顺延为第二步。
2. ✅ 批量导入**不自动生成卡**，另做"补卡"操作手动触发（一次导入几十条 × 同步调 AI，时间和费用都成倍涨）。
3. ✅ 毕业设计：stage 7 通过后永远按 60 天循环，不设终点 → 无需 status 字段。
4. 原第 9 节两问保持不变，属于爬虫开工前的事。

### 10.6 表结构定稿与落地记录（2026-10-11）

与 10.3 草稿的差异：**去掉 status**（毕业即循环）、**补 created_at**、**补到期索引**。定稿 DDL：

```sql
CREATE TABLE IF NOT EXISTS review_card (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    knowledge_id     INTEGER NOT NULL,            -- 逻辑外键：SQLite 外键默认不生效，完整性由 service 层保证
    question         TEXT NOT NULL,               -- 蒸馏拷贝（反范式化：自包含、可独立于知识原文存活）
    answer           TEXT NOT NULL,
    stage            INTEGER NOT NULL DEFAULT 1,  -- 1~7，语义属于 FixedLadderScheduler；换算法时此列随新算法演进
    next_review_at   TEXT NOT NULL,               -- 存"答案"不存推导；ISO-8601 文本字典序=时间序
    last_reviewed_at TEXT,                        -- NULL = 从未复习，不用魔法值冒充
    created_at       TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_review_card_due ON review_card(next_review_at);
```

定稿关键决策回顾：① question/answer 存蒸馏拷贝（反范式化）② next_review_at 可推导仍要存（最热路径走索引 + 对算法演进更稳）③ 逻辑外键不开强制 ④ 无 status ⑤ review_log 推迟（追加型表，随时可补，推迟零成本）。

已落地文件（编译通过）：
- `src/main/resources/schema.sql`（建表 + 索引，IF NOT EXISTS 幂等可重复启动）
- `src/main/java/com/example/kb/review/ReviewCard.java`（实体）
- `src/main/java/com/example/kb/review/ReviewCardMapper.java`（@Mapper 接口；项目未配 @MapperScan，靠 starter 自动扫描主类包下 @Mapper，换包位置仍生效）
- `src/main/resources/mapper/ReviewCardMapper.xml`（insert / findDue / findByKnowledgeId / findById / updateSchedule；XML 内 `<=` 须转义 `&lt;=`）

包结构说明：新功能采用 feature 包（review/ 全家桶），与既有 layer-first（entity/、mapper/、service/、controller/）并存——既有代码不动，新功能关进自己的包，仍是"复用能力、隔离边界"。等 collector 立项时照此办理。Mapper 接口刻意只留 5 个方法、没有 delete：删除等真实需求出现时再加（YAGNI）。

下一步（第 0 步余下，**2026-10-31 更新：已完成**）：ReviewScheduler 接口 + FixedLadderScheduler → ReviewService（到期查询/自评更新）→ ReviewController → 复习页 `/review` → 首页 `ReviewBanner` 到期提醒。
与实际实现的两处偏差，以代码为准：① 生成卡片**没有挂进** `KnowledgeService.add`，改为详情页手动「生成复习卡」按钮（批量导入不该触发 N 次 AI 调用）；② 到期提醒做的是**首页横幅**，没有做 `@Scheduled` 定时推送；开机自启在改为云端部署后不再需要。

## 附：本次讨论沉淀的可迁移思维

- 需求频率由消费者决定，警惕"实时"工程自嗨
- 通知疲劳是信息类产品的头号杀手；限额即克制即生命力
- 速率 > 存量（star 增速思维可迁移到很多数据判断）
- 漏斗的本质：把贵的处理（AI）放在便宜的粗筛之后
- 多家独立信源交叉印证 = 重要性信号
- 可解释性 → 信任 → 反馈数据 → 系统进化，是一个正循环
- 加新源不改主流程：面向接口编程 / 开闭原则的真实体感
- 复用能力但隔离边界：单体项目的包纪律
- 项目拆步的标准：每步结束都是完整闭环，防止烂尾
- 主动回忆（检索练习）> 重读；"一问一答"的卡片形态比复习日程本身更重要
- 先跑通再变聪明：算法先土后优，藏进接口实现里随时可替换
- 本地系统的所有"提醒"都依赖进程存活——基础设施问题（开机自启）先于功能问题
- 制卡摩擦是复习工具弃坑第一死因 → 自动化生成才是护城河
- 前置依赖的硬约束要在设计期暴露（"后端必须活着"），别等实现期撞上
